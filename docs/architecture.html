An Architecture Study

Designing an AI Incident Response Agent

An incident-response agent is not a runbook with an LLM bolted on. It is a fan-out of specialist reasoners over a live signal, grounded in retrieved system context, with every action written to one time-ordered spine — because the one thing more dangerous than a slow response is a wrong one at 3 AM. This study derives that architecture from first principles.

Part 0 · The Thinking Mindset

The lens before the system

Four reusable instruments, none specific to incidents yet.

Before any incident-response-specific design, four reusable instruments. A template that turns any messy workflow into an agentic system. A catalog of the ways agentic systems fail. A spectrum for deciding how much human stays in the loop. And a lifecycle that scaffolds the whole build. None of these are about incidents yet. They are the way of seeing that the rest of the study uses.

How do you design an agent that responds to an outage as reliably as a careful senior SRE — and proves its work when the post-mortem starts?
0.1

The Universal Design Template

After enough systems, intuition becomes a repeatable process. Five moves turn any workflow, in any domain, into an agentic design. We will apply all five to incident response in Part I.

Move 1. Map the mess

Document what actually happens today, not the runbook nobody follows. Watch the on-call SRE at 3 AM. Record the trigger that wakes them, every tab they open, every dashboard they check, where they are actually thinking versus mechanically shuffling information, and where the process breaks.

Move 2. Name the trigger and the output

Every automatable workflow has a precise trigger and a precise output. "A PagerDuty page fires with severity ≥ P2," not "an alert comes in." "A structured triage report is posted to the incident Slack channel," not "the on-call responds." If you cannot state both in one sentence each, you have not looked closely enough.

Move 3. Assign components

Take each step and assign it to a component type. Detecting that work is needed is a trigger. Fetching logs, metrics, or deploy history is a tool/API. Reading unstructured input (log lines, error traces) or writing language (the summary) is an LLM. A score or classification that must be identical every time — severity, blast radius category — is deterministic ML. A judgment that could bring down production if wrong — a rollback, a database migration — is a human checkpoint.

Most common mistake. Assigning an LLM to a step that should be deterministic. If the output must be the same every time given the same input — a severity score, a routing class, a runbook match — it must be deterministic. If the output is language and some variation is acceptable, it can be an LLM.

Move 4. Choose autonomy

Decide how much the system does on its own versus how much it defers to a human. This is not a default — it is a design choice driven by the consequence of error. Section 0.3 gives the full spectrum. In incident response, this choice matters more than almost anywhere: the system can post an analysis autonomously, but it must never execute a rollback without a human.

Move 5. Design for failure

Walk each component and break it on purpose. What happens when the LLM hallucinates a root cause, the log API times out, two parallel agents contradict each other on severity? Every component should fail gracefully.

The system should degrade to slower but correct, never fast but wrong. The worst failure mode is a wrong diagnosis delivered with confidence at 3 AM, because a groggy human will believe it.

0.3

The Human-in-the-Loop Spectrum

Not every system needs the same level of human involvement. The right level is a design choice, not a default. Five levels, and the three factors that pick one.

LevelDescriptionWhere it fits
Full automationSystem handles everything; human samples periodicallyRoutine, low-stakes, reversible work
Human reviews outputSystem produces, human verifies before it goes outDrafts with reputational stakes
Human handles exceptionsSystem auto-handles easy cases, human sees the hard onesAnomalies, low-confidence cases, escalations
Human decides, system preparesSystem gathers all context, human makes the callHigh-consequence, irreversible decisions
Full human with AI assistHuman does the work, system helps at specific stepsEarly-stage, low-trust, or creative work

Three factors choose the level. Consequence of error: a wrong severity label is annoying; an autonomous rollback of a stateful service is catastrophic. Reversibility: a Slack message can be edited; a dropped Kafka topic cannot be un-dropped. System maturity: new systems need more oversight; proven ones earn less.

Start with more human involvement than you think you need. Reduce it as the system proves itself. It is far easier to remove a checkpoint than to recover from removing it too early — and in production incidents, "too early" can mean an outage caused by the tool built to prevent them.

Part I · First Principles

Why automated triage exists, before how it works

Ten levels from "why this exists" to the full mental model.

Most people ask how to build an incident response agent. The better question is why one exists at all, because once you can answer that, the architecture becomes almost obvious. This part climbs from that first principle to a complete reasoning model in ten levels.

Read it twice. The first time for the incident agent. The second time for the method — the order of questions a strong engineer asks when handed any system they have never seen. Each level ends with the question we ask (the reusable move) and carry into the architecture (the concrete piece we keep). By the end those pieces assemble into one design.

A PagerDuty alert fires at 3:04 AM. A webhook lands. What, exactly, should happen next — and why?
L0

Why This System Exists

Imagine an on-call rotation without any automated triage. Every alert wakes a senior SRE. That attention is the scarce resource: it is slow (context-gathering takes 10–20 minutes before any diagnosis), inconsistent (a groggy 3 AM engineer misses signals an alert one hour into a shift would catch), and expensive (in wall-clock recovery time, in engineer burnout, and in every minute of a P1 that the business is losing money). The cost is not "no response happens" — it is that the most expensive, most valuable human time on the team is spent on the mechanical parts of triage before the actual thinking begins.

So an automated responder exists to solve exactly one problem: reclaiming the on-call SRE's context-gathering attention by automating the mechanical parts of triage, so the human is spent only where judgment is genuinely required — deciding what to do, and doing it.

An incident agent is not a replacement for human judgment. It is a way to spend human judgment only where it is actually scarce — the moment the human wakes up, joins the war room, and reads the agent's structured brief instead of running kubectl logs for the first ten minutes.

Hold onto the word selective. The system should not flood the incident channel with every conceivable signal. It should surface high-value findings with confidence and rationale, and route uncertain ones as questions to the human. That selectivity is the seed of the whole architecture.

The question we ask

Why does this system exist at all, and what single cost or loss does it remove?

Generalizes to: before any component, name the one scarcity the system relieves. A search system relieves the cost of not finding; a payments ledger relieves the cost of disputed truth; an incident agent relieves the cost of unstructured 3 AM context-gathering. If you cannot name it, you are designing a feature nobody needs.

Carry into the architecture

A selective, high-value posture. The system optimizes for surfacing findings worth an SRE's attention and deferring the rest — not for maximum output. Selectivity, not coverage, is the first principle.

L1

Start From How a Senior SRE Diagnoses

Before touching LLMs, prompts, or vector databases, ask how a senior SRE actually diagnoses an alert. When you are designing something genuinely hard, look for a system that already solved it. Human incident triage has been refined over decades of running production, and the structure we need is sitting inside how a good on-call thinks.

Watch one closely. They do four things that a naive single-prompt responder does not. They gather system context — recent deploys, current traffic, feature-flag state, known ongoing incidents. They reason across separate concerns — a symptoms pass (what is breaking), a change-correlation pass (what changed recently), a metrics pass (what the numbers say), a comms pass (who needs to know now). They stay skeptical — they do not assume the alert message is telling the truth. And they cite evidence — "the p99 latency spiked at 03:04:22, which matches the deploy timestamp of pod-checkout-7c9," not "looks like the deploy did it."

Read those four again as an engineer. "Gather system context" means the agent needs retrieval and tool calls into observability systems. "Reason across separate concerns" means the agent is not one reasoner but several. "Stay skeptical" and "cite evidence" mean every finding needs a rationale and a confidence.

Symptoms specialist — "what is actually breaking?"

Reads the alert, the immediately-preceding log lines, the current error rate, the affected endpoints. Distinguishes the failing surface from the alert's summary text (which is often stale or wrong).

Change specialist — "what changed recently?"

Reads deploy history, feature-flag changes, config-map updates, cron-job runs, migrations, third-party API status pages. In production, the answer is almost always "something changed" — this specialist finds it.

Metrics specialist — "what do the numbers say?"

Queries Prometheus / Datadog / New Relic for the affected service, correlates against baselines, identifies the earliest deviation timestamp. Turns "the service is slow" into "p99 latency doubled at 03:04:22, 47 seconds before the alert fired."

Comms specialist — "who needs to know, and what do they need to know?"

Drafts the two artifacts a human on-call always writes: (a) the customer-facing status-page update if it clears the threshold, and (b) the internal channel message with the current diagnosis, blast radius, and next steps.

The question we ask

Is there a mature system — human or engineered — that already solved a version of this, and what structure can I borrow from it?

Generalizes to: analogies hand you a ready-made decomposition. A recommendation system borrows from word of mouth; a cache borrows from working memory; an incident agent borrows from how a senior on-call actually thinks at 3 AM.

Carry into the architecture

Four specialist concerns, born from how a human triages. The system is not one reasoner but four — symptoms, change, metrics, comms — each a distinct pass with its own mindset. This is the seed of the multi-agent design.

L2

Map the Mess

Now apply the Part 0 template. Map the mess of what happens on an alert today: PagerDuty fires, the SRE fumbles for their laptop, opens six tabs (logs, metrics, deploy history, Slack, the runbook wiki, the status page), reads for ten minutes, then finally starts thinking. The reading is pure cost.

Name the trigger and the output. The trigger is precise: a PagerDuty (or Opsgenie, or Grafana OnCall) webhook fires with a payload containing incident_id, severity, service, and alert_summary. The output is precise too: a single structured triage report, posted back to the incident's Slack channel within 90 seconds of the trigger, with findings attached to specific services, timestamps, and evidence sources.

That word structured is doing strategic work. A triage report is not a blob of prose. It is a list of findings, each with a shape: which specialist raised it, how severe, what timestamp, what service, why, what evidence link, and how sure the agent is. Deciding that shape now is what lets every later component — the aggregator, the HITL gate, the audit trail — do its job. A first cut of that shape:

agent_type / which specialist raised this

symptoms, change, metrics, or comms — so findings can be grouped and attributed.

severity + category / how bad, what kind

P0 down to INFO; a category like deploy-regression, upstream-failure, capacity, data-quality.

service / timestamp / affected surface

The service name (canonical, from your service catalog), the earliest evidence timestamp, and the surface (endpoint, queue, batch job) — so the finding is actionable, not "something's wrong somewhere."

evidence + confidence + rationale

A link to the exact log line, dashboard, or deploy record that backs the finding. Confidence drives the HITL gate. Rationale is what makes the finding auditable in the post-mortem — because there will be a post-mortem.

The question we ask

What is the precise trigger, the precise output, and the shape of the object that travels between every component?

Generalizes to: a system is components plus the contract between them. Name the trigger and the output first, then name the object on the arrows. The object usually matters more than the boxes.

Carry into the architecture

An ingress trigger and a structured findings contract. The trigger is a PagerDuty webhook; the output is a structured triage report. The unit that flows through the system is a Finding with agent_type, severity, category, service, timestamp, evidence_url, confidence, and rationale.

L3

Industry-Standard Thinking

Most people picture one arrow: alert in, LLM, Slack message out. That is not how a capable incident system works, and the gap between those pictures is the gap between a demo and a system you would actually page at 3 AM. Walk the rungs of how the industry has climbed toward incident automation, and watch why each prior rung falls short.

RungWhat it doesWhy it falls short
Runbooks + wikiMatch alert to a documented procedure; human executesWikis rot within weeks of the last incident that touched them. No grounding in live state.
Rule-based automation (Rundeck, StackStorm)Match alert pattern to a scripted response; auto-remediate simple casesCannot reason about novel failures. Explodes into a rule-per-incident mess by year two.
Single-LLM triageOne prompt reads the alert + logs and drafts a summaryOne mindset for four concerns; no grounding in the system's real state; hallucinates root causes with confidence; no audit trail.
Agentic fan-outSpecialist agents, each grounded in the right data source, each skeptical, merged by an aggregatorThe rung this design stands on — but it demands orchestration, retrieval, tool-scoping, and a proof layer.

The single-LLM rung is the seductive one, because it works in a demo. It collapses four concerns into one prompt, which means it does each of them shallowly, and it has no way to be grounded in the live system, audited against the runbook, or trusted with even a Slack post at scale. The fan-out rung — running the four concerns from L1 as parallel specialists — is where production lives.

The question we ask

What does the mature version of this decompose into, beyond the happy path the demo shows?

Generalizes to: every interesting system has a hidden back half. List the rungs the industry has already climbed, and stand on the highest one whose cost you can actually pay.

Carry into the architecture

Parallel specialists, not a single prompt. The four concerns from L1 run as four agents in parallel, each doing one job deeply against its own data source. This is the agentic fan-out, and it implies an orchestrator and an aggregator we will name later.

L4

The Grounding Problem

Here is where most single-LLM incident responders fail. An LLM handed an alert message in isolation knows what the alert says but nothing about the system it fired against. It cannot know that the checkout-service was deployed 90 seconds ago, that a feature flag flipped at 03:02, that the same alert fired last month and turned out to be a Redis eviction storm. So it does what models do under uncertainty: it guesses, confidently. That is hallucination in a critical path — the first failure mode from the 0.2 catalog, and the most dangerous one in incident response, because a groggy human at 3 AM will act on a confident wrong answer.

A senior SRE does not have this problem because they know the system. The design question is: what gives the agent that knowledge? It cannot be the full observability stack in the prompt — that exhausts the context window on any non-trivial infrastructure, and most of it is irrelevant to a given alert. The answer is retrieval + tool calls: for each alert, fetch only the most relevant slices of live system state, and put those in the prompt.

An ungrounded responder is a confident stranger at 3 AM. A grounded one is the senior SRE who has already been paged on this service twice this quarter. Retrieval is what turns the stranger into the colleague — and tool-calling is what lets the colleague ask "what's the current p99?" instead of guessing.
The question we ask

What does this reasoner need to know that is not in front of it, and how do we put exactly that — and only that — in front of it?

Generalizes to: any LLM judging an artifact in isolation hallucinates. Retrieval-augmented generation is the general fix — fetch the relevant context, do not dump everything, do not assume the model already knows.

Carry into the architecture

A retrieval + tools layer. Each specialist queries for the context relevant to the alert — past incidents (RAG), runbooks (RAG), and live state (Prometheus, deploy history, feature flags — via tool calls). Grounding is not optional; it is what separates this from a single-LLM demo.

L5

What Kinds of Memory Does Triage Need?

L4 said "retrieve context." But context is not one kind of thing. A senior SRE draws on several kinds of memory, and — exactly as in cognitive science — each kind has a different shape and a different access pattern. Naming them now is what determines the data design later.

Kind of memoryWhat it holds for triageThe data shape it wants
SemanticRunbooks, past incident post-mortems, architecture docs, service ownership — as meaningVector embeddings + similarity search
EpisodicPast triage runs — which alerts fired, what the agent said, what the human decided, whether they overrodeTime-stamped relational rows
ProceduralTeam conventions, severity policy, service-to-team mapping, escalation rulesSmall, high-priority, almost always loaded
Live-stateThe current p99, the last deploy, the current feature-flag state, the current queue depthNot stored — fetched per triage, via tool calls

Read those four again as an engineer. Semantic memory wants similarity search over embeddings — a vector store. Episodic memory wants time-ordered, queryable rows — relational history. Procedural memory is small and structured — facts and rules. And live-state is not memory at all — it is a tool call, because a value that is 60 seconds stale is worthless in an incident.

The taxonomy is not philosophy; it is a schema waiting to be written, and it tells us we do not have one data need but three distinct stored shapes plus a live tool-call layer.

The question we ask

What distinct kinds of state does this system hold, and does each kind want a different shape rather than one undifferentiated bucket?

Generalizes to: before choosing storage, enumerate the kinds of state by access pattern. Hot vs cold, similarity vs exact, append-only vs mutable, stored vs fetched-live. The kinds drive the shapes; the shapes drive the stores.

Carry into the architecture

Three stored shapes plus one live layer. Semantic memory of runbooks and post-mortems wants a vector / ANN shape. Past triage runs want a relational shape. Conventions and policies want a small structured shape. And live production state is never stored — it is fetched per triage via a tool-registry we will design in Part III.

L6

Trust and Proof

Suppose the agent posts a finding: "the outage is caused by the checkout-service deploy at 03:03:14, confidence 0.72." The SRE on-call trusts it, initiates a rollback — and the outage gets worse, because the real cause was a downstream vendor's API. The post-mortem asks the obvious question: why did the agent say that, and what evidence did it have? If there is no record of which context was retrieved, which prompt version ran, what the model returned, what tools were called, and what they returned — the system cannot defend itself, cannot be debugged, and cannot improve. A triage you cannot audit is worthless, and one whose cost can run away unobserved is dangerous.

So trust requires a third thing beyond reasoning and grounding: proof. Every action the agent takes — every span of work, every LLM call, every tool call, every decision — must be recorded as an event, in time order, durably. That single stream of events is what powers three things at once: a trace viewer (reconstruct any triage end-to-end), an audit trail (defend or dispute any finding), and a cost ledger (attribute every token to a specialist and a model).

If the system cannot show its work, it has not done the work. In incident response, the proof layer is not instrumentation bolted on at the end — it is born here, as a first principle, the moment we ask a machine to advise a human at 3 AM on whether to roll back production.
The question we ask

When this system produces an output, can it prove how it got there — and can it tell us what that cost?

Generalizes to: any system making consequential automated decisions needs an immutable, time-ordered record of its actions. Payments, fraud scoring, medical triage, production incidents. Design the audit stream with the decision, not after the incident.

Carry into the architecture

An events spine. Every action becomes a time-ordered event row — span, LLM call, tool call, decision — carrying cost, latency, confidence, and outcome. One stream feeds the trace viewer, the audit trail, and the cost ledger. This is a fourth data need, time-series in shape.

L7

When Not to Trust It

L0 said the system should be selective. L6 gave it the confidence field. Now apply the 0.3 HITL spectrum to this system. The agent is not always right, and it knows roughly when it is unsure — that is what the confidence on each finding measures. The design decision is what to do with that knowledge — and in incident response, this is the most consequential design decision in the whole system.

The answer is a confidence-weighted gate, layered with a hard rule: the agent never executes production actions autonomously. It can post analysis. It can suggest a rollback. It can pre-fill the rollback command in Slack for a human to click. It cannot press the button. That is not a technology choice — it is a values choice, because the consequence of a wrong autonomous rollback exceeds the consequence of a slower human-approved one.

ConditionActionWhich 0.3 factor
High-confidence read-only analysis (all findings ≥ 0.75)Post automatically to incident channelMaturity earns autonomy; reversible action
Any finding below 0.75Post to channel with explicit "low confidence" tag; route to on-call for verificationUncertainty, defer judgment
Any P0 severity or write-action suggestionRoute to human approval; suggested action is pre-filled but not executedConsequence of error too high; irreversibility
Human overrides the agent's diagnosisStore override + reason as feedback; increase weight on human input for similar future signalsLearning loop, reversibility
The question we ask

Where on the human-involvement spectrum does this system belong, and what signal moves a given case up or down it?

Generalizes to: autonomy is not binary. Let the system earn it case by case, gated on a confidence signal and the stakes. Content moderation, lending, triage — all use the same confidence-weighted routing. Incident response tightens it further by adding a hard rule: read-only actions can be automatic; write-actions never are.

Carry into the architecture

A two-layer HITL gate. Layer one: confidence-weighted routing for read-only outputs (post autonomously above threshold; tag as low-confidence below). Layer two: all write actions require human approval, regardless of confidence. The gate implies queue and feedback tables in the relational shape from L5, and a pre-filled-but-unexecuted action pattern.

The question we ask

For each component, what happens when it fails, and does the system degrade to slower-but-correct rather than fast-but-wrong?

Generalizes to: run a pre-mortem before code. Walk each box and break it on purpose. The fallbacks you design now are the incidents you avoid later — and in a system designed to respond to incidents, this discipline is not optional.

Carry into the architecture

A reliability layer. Timeouts on every tool and LLM call, circuit breakers on external sources, idempotency at ingress, dead-letter queue on the orchestrator, cross-specialist agreement scoring in the aggregator, and priority queuing on the human approval channel — each mapped to a specific failure mode, not added speculatively.

L9

The Mental Model

Before we draw a single box, the assembled reasoning in prose. The pieces we carried, in the order they were earned, already describe the whole system.

A PagerDuty alert triggers the work (L2). It is enqueued, not handled inline, because the trigger must be acknowledged fast and the work decoupled from the ingress (L2, L8). An orchestrator fans the work out to four specialists — symptoms, change, metrics, comms (L1, L3) — running in parallel. Each specialist is grounded by retrieval over runbooks and past incidents (L4, L5), and by tool calls into live observability systems (L5). The runbooks, the past triage runs, the conventions, and the live state are four distinct kinds of context (L5). Each specialist returns structured findings with confidence, evidence, and rationale (L2). An aggregator merges them, computes cross-specialist agreement, applies the HITL gate (L7): post read-only analysis autonomously when confident, tag as low-confidence otherwise, and never execute write-actions without human approval. Every action along the way is written to an events spine (L6) so the whole thing can be traced, audited in the post-mortem, and priced. And a reliability layer (L8) keeps each step degrading to slower-but-correct.

Now ask: how many databases does this need? We have memory, truth, and time. The naive answer is three durable stores. Part II interrogates that answer — and arrives at one.

L7A two-layer HITL gate: confidence-weighted for read-only; hard human approval for all writes.
L8A reliability layer: timeouts, circuit breakers, idempotency, dead-letter, priority queue.
L9The assembled mental model — and the open question: how many databases?
Part II · From Principles to Data

Why one Postgres, not three databases

Vector, relational, and time-series in one spine.

This is the heart of the data design. The agent needs runbook memory, durable triage truth, and a time-ordered trail of what every specialist did. The reflex is to buy one database for each need — Qdrant for vectors, plain Postgres for triage records, Timescale or ClickHouse for events. This part slows that reflex down and asks a simpler question: can one Postgres-compatible store carry all three shapes without making the system harder to understand?

Most AI systems split memory, truth, and time across separate databases. What if one is enough — and clearer?
2.1

Three Data Shapes, One Reflex

Do not start by naming databases. Start by naming what the product has to remember.

The agent has three stored data shapes. First, memory: chunks of runbooks, past post-mortems, and service documentation that help the agent understand a new alert. Second, truth: the triage record, the findings, the incident-channel post ID, and any human decision or override. Third, time: every span, LLM call, tool call, cost, latency, and decision in the order it happened.

There is also one reflex that makes the system feel simple: read before action, write after action. Before the agent speaks, fetch relevant runbook memory and live tool data. After the agent acts, write the triage truth and the event trail.

The naive architecture maps each shape to a purpose-built store. Qdrant for vectors, plain Postgres for triage records, ClickHouse for events. Redis still sits alongside for the queue and orchestrator checkpoints.

Data shapeReflexive storeWhat it holds
MemoryQdrantEmbedded runbook + post-mortem chunks for semantic retrieval
TruthPostgresTriage runs, findings, HITL rows, incident-channel IDs
TimeClickHouse or TimescaleSpans, LLM calls, tool calls, cost, latency

That sounds clean until you ask one product question: "For this triage run, what runbooks did we retrieve, what diagnosis did we produce, and which model calls made it expensive?" With three stores, the app has to query three systems and stitch the answer together in application code. That is the cost: more connection pools, more backups, more failure modes, and no simple joins.

The question we ask

Can we keep the three shapes, but not split them across three durable databases?

Generalizes to: any system tempted to add a new datastore per feature. The right first move is not "which database is popular?" It is "what shape is this data, and does the current store already handle it well enough?"

Carry into the architecture

Three shapes, one reflex. Memory, truth, and time are requirements. Separate databases are only an implementation choice. The next section asks whether Postgres with the right extensions can carry all three.

2.2

One Store, Not Three

The key sentence is: Postgres with the missing powers added. Managed Postgres with three extensions handles all three shapes. This is not "one database is better than three" as a dogma. It is: one durable data spine, until a shape proves it cannot live there.

Plain Postgres already handles the truth lane well: triage rows, finding rows, foreign keys, transactions, and normal SQL. To absorb the other lanes, it needs three additions. Each addition has a simple job.

1. Vector search for memory — pgvector + pgvectorscale

Runbooks and past post-mortems get turned into embeddings — 256-dimensional vectors of numbers. Semantically similar content gets similar vectors. pgvector stores that list in a real Postgres column. pgvectorscale adds a DiskANN index so lookups stay fast into the millions of chunks. When a new alert fires, the agent embeds the alert-plus-context and asks Postgres: which stored runbook chunks are closest?

2. Time-series storage for the events spine — TimescaleDB

Every agent event has a timestamp and is naturally time-ordered. A TimescaleDB hypertable partitions the events table by time behind the scenes — recent chunks stay hot, old chunks compress. To the application it still looks like one table.

3. Rollups for dashboards and budget checks — continuous aggregates

A dashboard should not count raw events from scratch every time it loads. A continuous aggregate is a summary table Postgres keeps updated: cost per specialist per minute, p95 latency, tokens per triage. The BudgetGuard reads the summary first — if today's spend is already above the daily cap, it hard-blocks before the next LLM call.

Redis stays. The Redis queue and orchestrator checkpoints are short-lived, high-churn workloads. They do not want vector search or hypertables. "One database" here means one durable data spine, not forcing every workload into SQL.
2.3

The Three Lanes, in Real Schema

"One database" does not mean one giant table. It means the same database holds different table shapes for different jobs. Here are the actual DDL sketches for the three lanes.

Lane 1 — Memory: knowledge_chunks

Runbook and post-mortem chunks live here. An ingestion job (Part IV, Phase 14) chunks each markdown document, embeds each chunk, and writes it. At triage time, the retrieval layer queries this table to find context relevant to the alert.

CREATE TABLE knowledge_chunks (
    id           UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    source_type  TEXT         NOT NULL,         -- runbook | postmortem | arch_doc
    source_id    TEXT         NOT NULL,         -- doc path or ID
    service      TEXT,                          -- owning service (nullable)
    chunk_index  INT          NOT NULL,
    content      TEXT         NOT NULL,
    embedding    VECTOR(256)  NOT NULL,
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX knowledge_chunks_emb_idx
    ON knowledge_chunks USING diskann (embedding vector_cosine_ops);

ALTER TABLE knowledge_chunks
    ADD COLUMN content_tsv TSVECTOR
    GENERATED ALWAYS AS (to_tsvector('english', content)) STORED;

CREATE INDEX knowledge_chunks_fts_idx
    ON knowledge_chunks USING GIN (content_tsv);

Vector search catches meaning; full-text search catches exact names like service names, error codes, and config keys. The retrieval layer uses both and merges by reciprocal rank fusion.

Lane 2 — Time: agent_events

Every agent action becomes one append-only row: span starts, span ends, LLM calls, tool calls, decisions, escalations, cost, latency, payload.

CREATE TABLE agent_events (
    ts            TIMESTAMPTZ  NOT NULL,
    triage_id     UUID         NOT NULL,
    specialist    TEXT         NOT NULL,   -- symptoms|change|metrics|comms|aggregator
    span_id       UUID         NOT NULL DEFAULT gen_random_uuid(),
    parent_span   UUID,
    event_type    TEXT         NOT NULL,   -- span.start|span.end|llm.call|tool.call|decision
    model         TEXT,
    tool_name     TEXT,
    tokens_in     INT,
    tokens_out    INT,
    cost_usd      NUMERIC(10,6),
    latency_ms    INT,
    outcome       TEXT,
    confidence    NUMERIC(4,3),
    payload       JSONB
);

SELECT create_hypertable('agent_events', by_range('ts', INTERVAL '1 day'));

Lane 3 — Truth: relational triage tables

Deliberately ordinary. triage_runs for one row per triage, findings for one row per finding, hitl_approvals for human decisions on write-actions, hitl_feedback for post-triage overrides. Standard relational shape because the data is standard relational data.

Carry into the architecture

One Postgres-compatible data spine. Managed Postgres (Timescale Cloud, Neon with pgvector, or self-hosted with the extensions) carries memory with pgvector/pgvectorscale, time with hypertables and continuous aggregates, and truth with normal relational tables. Redis stays for the queue and orchestrator checkpoints.

Part III · The Architecture, Assembled

Now, and only now, the boxes

Every box was earned in Parts I and II.

Every box below was earned in Parts I and II. As each section opens, it names the principle it fell out of. The diagrams are the carried pieces, drawn. Nothing here is new — it is the reasoning model made concrete, in the JVM stack.

3.1

Ingress & the Queue

From the ingress trigger and the decoupling we carried at L2 and L8: a PagerDuty webhook arrives, is validated, and is enqueued — never handled inline.

The ingress handler is a Spring Boot @RestController at /webhooks/pagerduty. It does exactly three things. It verifies the PagerDuty HMAC-SHA256 signature on the payload, rejecting forgeries before any work. It checks the idempotency key (incident_id + payload hash) so a retried delivery is acknowledged and dropped rather than triaged twice — the idempotency defense from L8. Then it enqueues the triage job to Redis (via Spring Data Redis + a lightweight consumer worker) and returns 200 immediately. PagerDuty expects a fast acknowledgment; the heavy work happens asynchronously in a worker.

PagerDuty │ ▼ webhook POST /webhooks/pagerduty ┌─────────────────────────────┐ │ INGRESS (Spring @RestCtl) │ │ · HMAC verify │ │ · idempotency check │ │ · enqueue(TriageJob) │───► 200 OK (acknowledge fast) └──────────────┬──────────────┘ │ ▼ ┌────────────────┐ │ Redis queue │ │ (Streams) │ └────────┬───────┘ │ ▼ ┌─────────────────────────────┐ │ ORCHESTRATOR WORKER │ │ (Java thread pool) │ │ · LangChain4j fan-out │ │ · specialists in parallel │ │ · aggregator │ │ · HITL gate │ │ · post to Slack │ └─────────────────────────────┘
Ingress validates and enqueues; the worker drives the orchestrator; the result posts to the incident Slack channel via the HITL gate.
Why not handle inline? A slow LLM provider or a crashed orchestrator would make the webhook endpoint time out. PagerDuty then retries. Retries without idempotency cause duplicate triage. The queue is not just about performance — it is a correctness boundary.
3.2

The Orchestrator

From the parallel-specialists fan-out we carried at L3: the orchestrator is a graph, not a pipeline. Specialists run simultaneously; state is checkpointed between them.

The orchestration is built on LangChain4j's workflow primitives, with a small custom graph layer for the parallel fan-out. A typed TriageState object flows through the graph. State is checkpointed to Redis at each node boundary, so a worker crash mid-triage resumes from the last completed node rather than restarting from the alert. The checkpoint store is the same Redis the queue uses — one fewer dependency.

The graph lives in the orchestrator package: TriageGraph.java wires the parallel fan-out and the aggregator join, TriageState.java defines the typed state, Nodes.java holds the node functions (buildContext, the four specialist nodes, aggregate). Each node has a timeout (default 30 seconds for tool-calling specialists, 45 for LLM-heavy ones). The aggregator is wired to run only after all four specialists complete or hit their timeout — this is the orchestration-deadlock defense from L8. A stalled Prometheus query cannot hang the whole triage forever.

Why not Temporal? Temporal would be more durable and would scale better. But it is a separate service, a separate worker pool, and meaningful ops overhead for a system that must be operable by one engineer. The design puts the orchestrator behind a narrow WorkflowEngine interface — swap the LangChain4j implementation for a Temporal one when scale demands it, without changing any specialist code.
3.3

Specialists & the Aggregator

From the four concerns we carried at L1 and the Finding contract from L2: four specialists run in parallel, each returning structured findings, merged by one aggregator.

The four specialists — SymptomsSpecialist, ChangeSpecialist, MetricsSpecialist, CommsSpecialist — share a base shape in BaseSpecialist.java (BudgetGuard check, retrieval call, tool calls, LLM call, event emission, error handling) and differ only in their domain prompt, their tool set, and their post-processing. Each returns a list of Finding objects (defined in Finding.java) matching the L2 contract: agentType, severity, category, service, timestamp, evidenceUrl, confidence, rationale.

Structured output is what makes the next step deterministic — the aggregator merges data, not prose. LangChain4j's structured-output support (via JSON schema constraints + validation) makes this reliable in Java in a way it was not two years ago.

The tool scoping matters

Each specialist has a restricted tool set (from L4 grounding + L7 HITL). The symptoms specialist gets read-only log and error-rate tools. The change specialist gets read-only deploy-history and feature-flag tools. The metrics specialist gets read-only Prometheus/Datadog query tools. The comms specialist has no external tools — it only reads the other specialists' findings and drafts the Slack + status-page text. No specialist has write tools. Write actions (rollback, restart, scale) are surfaced as suggestions in the aggregator's output and require HITL approval.

The aggregator merges all four lists, deduplicates findings that multiple specialists raised on the same service and timestamp (keeping the highest-confidence one and boosting confidence when specialists agree), computes an overall_confidence, and applies the L7 HITL gate: post read-only analysis to Slack when confident, tag as low-confidence when not, and route any suggested write-action to the human approval queue.

3.4

The Retrieval Path

From the grounding problem at L4 and the data shapes at L5: each specialist queries the vector lane for runbook context relevant to the alert. Retrieval is hybrid — vector and keyword in parallel, merged by reciprocal rank fusion.

The retrieval layer lives in the memory package: KnowledgeRetriever.java, Embedder.java (calling OpenAI or a self-hosted embedding model via LangChain4j), and HybridSearch.java. Pure vector search finds meaning but misses exact identifiers; pure keyword search finds exact strings but misses semantic relevance. The layer runs both against knowledge_chunks: DiskANN ANN search over the 256-dim embeddings, and full-text search over the content_tsv GIN index. RRF merges the two result sets and returns the top-k chunks into the specialist's prompt.

3.5

The Events Spine in Operation

From the trust-and-proof principle at L6: every action is one row in agent_events, and three consumers read that one table.

The observability layer (EventEmitter.java, Tracing.java, AuditReader.java) emits an event for every span, LLM call, tool call, and decision, carrying the span_id/parent_span chain, cost, latency, confidence, and outcome. The trace viewer reconstructs any triage with SELECT * FROM agent_events WHERE triage_id = ? ORDER BY ts. The audit trail is the same append-only table, immutable by construction — critical for post-mortems. The cost ledger reads the continuous aggregates — and so does the BudgetGuard, which reads the day's running cost at the top of every specialist run and hard-blocks before any LLM call if the daily cap is exceeded.

Closing

How to reuse this

The architecture was the example. The method is the takeaway.
5.1

The Transferable Framework

Collect the "question we ask" moves from the climb. None of them mention incident response. Each applies to whatever you build next.

  1. Why does this system exist? Name the one scarcity it relieves, or do not build it.
  2. What mature system already solved a version of this? Borrow its decomposition.
  3. What is the precise trigger, output, and the object on the arrows? The contract matters more than the boxes.
  4. What does the mature version decompose into? Find the hidden back half; stand on the highest rung you can afford.
  5. What does this reasoner need that is not in front of it? Retrieve exactly that, and only that.
  6. What distinct kinds of state, by access pattern? Kinds drive shapes; shapes drive stores. And some state is not stored at all — it is fetched live.
  7. Can it prove how it got there, and what it cost? Design the audit stream with the decision, not after.
  8. Where on the autonomy spectrum, and what signal moves a case along it? Let the system earn trust case by case — and where writes touch reality, keep the human always.
  9. What happens when each box fails? Degrade to slower-but-correct, never fast-but-wrong.
  10. Count the data shapes before the databases. One store until a shape proves it cannot live there.
  11. Can the hard decision hide behind an interface? Make the cheap choice now; swap one file later.
Design is not a parts list. It is a chain of questions, each one earning the next box. If a component cannot be traced back to a question you can defend, it is either missing a justification or it does not belong.

Notice that the most consequential architectural decision in this study — collapsing memory, truth, and time onto one Postgres spine — fell out of question ten, not out of a preference for any product. The store was derived, lane by lane, because the data shapes fit one Postgres-compatible database with the right extensions. That is the posture to carry: let the data shapes, the failure modes, and the proof requirement choose the architecture, and defend each choice on its merits.
